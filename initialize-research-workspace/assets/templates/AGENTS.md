## Program directories and Git

- Develop new ideas, trial scripts, and programs under evaluation in `PROG_temp/`. Once the owner confirms a program is suitable, promote the specified program and its required dependencies into the active formal directory. Maintain existing formal programs in the registered active directory.
- Start with `PROG1/` for the first formal model. When the owner confirms adoption of a new model, create the next numbered directory and update the register. Use the model's own Git history for routine revisions within the same model.
- Each numbered formal directory is an independent local Git repository. Keep `PROG_temp/` free of a repository of its own. Preserve existing repositories and their histories. The owner decides when to make an initial commit, configure remotes, or push.
- After switching models, treat earlier formal directories as read-only archives. Use the program's own directory and dependencies when running it. If the owner explicitly requests work on an archived version, follow the requested path and scope.

## Data and deliverables

| Output | Default location |
| --- | --- |
| Data, figures, tables, logs, and verification results generated by a formal program | The producing formal directory's `output/` |
| Results generated by an exploratory program | `PROG_temp/output/` |
| Project-level deliverables such as meeting notes, presentation materials, and review comments prepared outside program runs | `output/` at the project root |

The producing program determines the output location. For example, a program in `PROG2/` that reads data from an older model writes its results to `PROG2/output/`. Keep source data at its recorded location. Resolve output paths relative to the program so the same entry point works when launched elsewhere.

For publication figures, use an independent plotting entry point that reads saved results. For example, keep a MATLAB entry point named `plot_<description>.m` in its formal model directory and place the exported figures and related verification materials in that version's `output/<task_name>/`. Check input data, display mappings, dimensions, and final rendering.

## Manuscripts, evidence, and continuity

- Before reviewing or editing a manuscript, locate the designated project and its current saved source. Edit within the owner's requested scope. For layout changes, inspect the affected pages of the resulting document.
- Verify precise values and parameters against the designated programs and original data. Use literature for definitions, methods, and related work. If a manuscript, program, dataset, or historical record disagrees with another source, identify the specific discrepancy for the owner.
- Report what actually took place, such as static review, a program run, numerical verification, simulation, or a physical experiment. Record verification status and inclusion in the current manuscript separately.
- Read the relevant topic in [CONTEXT.md](CONTEXT.md) when resuming research progress, prior decisions, advisor feedback, or future plans. Before closing a conversation with a lasting development, propose the specific additions, revisions, or retirements and their evidence. Update the record only after the owner explicitly agrees to those changes.
- Consult [TERMINOLOGY.md](TERMINOLOGY.md) when preparing project materials. Before registering a new term or revising an approved expression, present the source term, context, proposed wording, and source for the owner's approval.
- Use the recipient's preferred language for project documents and the language requested for each deliverable. Preserve filenames, paths, commands, code identifiers, and scientific symbols when localizing text.
- Update this file when long-term agreements or the project register change. Record individual research developments in the research log and locate technical details through its source index.
