## Program directories and Git

- Develop new ideas, trial scripts, and programs under evaluation in `PROG_temp/`. Once the owner confirms a program is suitable, promote the specified program and its required dependencies into the active formal directory. Maintain existing formal programs in the registered active directory.
- Start with `PROG1/` for the first formal model. When the owner confirms adoption of a new model, create the next numbered directory and update the register. Use the model's own Git history for routine revisions within the same model.
- Each numbered formal directory is an independent local Git repository. Keep `PROG_temp/` free of a repository of its own. Preserve existing repositories and their histories. The owner decides when to make an initial commit, configure remotes, or push.
- Use Git to version the model's code. Add `/output/` to the root `.gitignore` of each new numbered model repository, keeping generated figures, files, and data on disk. If the project repository manages a model directly, use a rule anchored to that model's actual output path, such as `/PROG1/output/`. Include any proposed ignore-rule changes for an existing project in the plan for owner approval. For outputs that Git already tracks, ask the owner to approve removal from the index and preserve the files on disk and the existing history.
- If a confirmed generated file must stay outside `output/` because of a tool or a path dependency, use an exact ignore path anchored to the repository that manages it. For example, use `/bifur.mat` in an independent `PROG2/` repository or `/PROG2/bifur.mat` in a shared project repository. Keep the project's existing tracking rules for input files, including `.mat` inputs.
- After switching models, treat earlier formal directories as read-only archives. Use the program's own directory and dependencies when running it. If the owner explicitly requests work on an archived version, follow the requested path and scope.

## Data, assets, and deliverables

| Item | Default location |
| --- | --- |
| Data, figures, tables, logs, and verification results generated by a formal program | The producing formal directory's `output/` |
| Results generated by an exploratory program | `PROG_temp/output/` |
| Simulator projects, schematics, netlists, and tool-specific scripts | `simulation/<tool>/` at the project root |
| Project-level deliverables such as meeting notes, presentation materials, and review comments prepared outside program runs | `output/` at the project root |
| Selected project figures for manuscripts, presentations, and reports | `figures/` at the project root |
| Available project literature and supporting references | `references/` at the project root |

Resolve a new program's default output path relative to the program file. For example, `PROG2/bifurcation_diagram.m` writes `PROG2/output/bifur.mat` even when launched from another working directory or when reading data from an older model.

Before reorganizing existing files, check their origin and use in read-only mode. Look for supporting scripts, run records, or dependencies, and ask the owner when needed. Show confirmed generated files in the proposed tree at their destination in the producing model's `output/`, with any affected references listed in the plan. Apply approved moves and reference updates together. Keep inputs and files of uncertain origin in place.

Create tool folders such as `simulation/LTspice/`, `simulation/Multisim/`, and `simulation/PSpice/` when the project uses those simulators. Keep each project with its required models, libraries, settings, and scripts. Manage general MATLAB and Python code under the applicable `PROG*` directory.

Before moving an existing simulation project, confirm the software and identify its dependencies and affected paths. Present the source and destination to the owner for approval, then verify that required files and references still resolve after the move.

For publication figures, use an independent plotting entry point that reads saved results. For example, keep a MATLAB entry point named `plot_<description>.m` in its formal model directory and place the exported figures and related verification materials in that version's `output/<task_name>/`. Check input data, display mappings, dimensions, and final rendering.

Keep generated originals in the producing program's output directory and place selected copies in `figures/`. Before organizing existing figures or literature, propose the source, destination, and operation for each item, and identify any affected code or manuscript references. Wait for the owner's approval. Keep in-use bibliography files in their current locations unless the owner approves their relocation and the corresponding reference updates.

## Manuscripts, evidence, and continuity

- Before reviewing or editing a manuscript, locate the designated project and its current saved source. Edit within the owner's requested scope. For layout changes, inspect the affected pages of the resulting document.
- Verify precise values and parameters against the designated programs and original data. Use literature for definitions, methods, and related work. If a manuscript, program, dataset, or historical record disagrees with another source, identify the specific discrepancy for the owner.
- Report what actually took place, such as static review, a program run, numerical verification, simulation, or a physical experiment. Record verification status and inclusion in the current manuscript separately.
- Consult [TERMINOLOGY.md](TERMINOLOGY.md) when preparing project materials. Before registering a new term or revising an approved expression, present the source term, context, proposed wording, and source for the owner's approval.
- Use the recipient's preferred language for project documents and the language requested for each deliverable. Preserve filenames, paths, commands, code identifiers, and scientific symbols when localizing text.
- Update this file when long-term agreements or the project register change.

## Research records

- Read [CONTEXT.md](CONTEXT.md) for overall progress, major decisions, and next steps. Follow links to detailed records when the task requires them.
- Before wrapping up research work, check for substantive progress, results, decisions, changes in direction, or corrections worth preserving. Propose the exact additions, revisions, or removals to `CONTEXT.md`, cite the supporting sources, and ask the owner whether to apply them. Update only the approved entries. Skip the prompt for routine work with no substantive developments.
- Record the owner's confirmed logging preferences in this section, including what to record, when to propose updates, and where to keep the records. Apply those preferences in future tasks.
- Create a detailed Markdown record when the project needs one. Choose a name, structure, and location that fit the work. Keep records about a program, simulator project, or asset near it. Use `context/` when it provides a natural home for a broader topic. Create that directory when the first record there is needed and approved.
- Reuse existing Markdown where it already serves the purpose. When it helps people navigate existing files, add a Markdown entry point that links to material in its original format, such as a CSV, YAML file, or generated log.
- Add a relative link from the relevant entry in `CONTEXT.md` for project-wide work or from a directory's existing documentation for local details. Link to the record once it exists.
- Propose significant additions, revisions, or moves to detailed records and identify the supporting sources. Update the records and affected links after the owner approves the changes.
